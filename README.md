# FreeAnalyst

**Open source. Air gapped. Off at six.**

自由分析师 · 免费分析师

---

一级市场投资的尽调 agent。完全跑在你自己的机器上——你的 CIM、会议纪要、估值逻辑、
条款清单，一个字节都不离开这台电脑。

## 为什么叫 FreeAnalyst

`free` 有两个意思，两个都成立。

**自由。** 它替你把该读的材料读完、该核对的数据核对完，把时间还给你。
九点到六点，也能做完一天的尽调。

**免费。** 没有订阅，没有席位费，没有 token 账单。模型跑在你自己的机器上，
工具是开源的。一个免费的分析师，全天候待命。

## 三个承诺，三种证明方式

| 承诺 | 怎么证明 |
|---|---|
| **代码全开源** | 所有代码在 GitHub 上，任何人都可以审计 |
| **默认零出境** | 全项目只有一个网络出口（`guard.py`）。默认只放行 `localhost`；要发给云端模型，得**按次显式授权**，且每次调用留审计日志 |
| **结论可追溯** | 每条结论强制带原文出处；材料里没有的一律写"未提供"，禁止推测 |

### 「默认零出境」是什么意思

有些材料要保密，有些不必 —— 所以**选择权在你**，但默认状态永远是最严的那一档：

| 目标 | 默认 | 怎么才能通 |
|---|---|---|
| 本地模型（`127.0.0.1`） | ✅ 放行 | 什么都不用做 |
| 云端模型（任何外部主机） | ⛔ **拦截** | 这一次调用必须带 `CloudConsent`——**绑定主机 + 用途 + 发出内容描述** |

**刻意不做全局开关。** 一个 `ALLOW_CLOUD=1` 之类的开关装完就一直是开着的，
「零出境」就成了空话。授权是**按次**的：拿「给这段纪要写摘要」的授权
去发整份材料，一样会被拦。

而且**授权这件事本身也写进审计日志**，连同**发出去的字节数和内容摘要** ——
事后能核实「那次到底发出去了多少、是不是同一份材料」。

第二个承诺不是口号，是可验证的：

```bash
python3 freeanalyst.py audit
```

```
  总调用   3
  放行     3  （应全部为回环地址）
  拦截     0
  外部主机 无
```

**`外部主机 无` 意味着：从第一次运行到现在，这个程序从未向你的机器之外
发起过任何一次请求。**

而 `拦截 0` 是因为目前还没有任何东西尝试出去。**想验证闸门真的拦得住，
跑 `python3 tests/test_egress_guard.py`** —— 它会拿 OpenAI、Anthropic、
Google、DeepSeek、阿里百炼的真实地址去试探，并确认全部被拦下且留痕。

```bash
$ python3 tests/test_egress_guard.py
Ran 5 tests in 0.020s

OK
```

## 两个域：机密域不出网，公开域拿不到机密

程序要联网（抓可比公司、查公开数据），但材料不能出去。这两件事怎么同时成立？

**靠能力隔离，不靠内容过滤。** 内容过滤做不到——你无法判断一段出境文本里有没有
夹带机密：

> "标的企业A、收入1.83亿、增速17.9%、行业只有三家可比"
>
> 这组数字本身就是指纹，把公司名替换成"A"没有用。

```
┌─ 机密域 ──────────────────┐        ┌─ 公开域 ──────────────────┐
│ corpus / root / 本地模型   │        │ 白名单数据源               │
│ guard.py：只放行 localhost │   ✕    │ net.py：只放行白名单主机    │
│ 审计日志：外部主机 无       │◄─────► │ 审计日志：只有公开查询词    │
└───────────────────────────┘        └───────────────────────────┘
                    ↑
            privacy.py：唯一允许跨域的入口
            出境值与本地语料逐字比对，重合即拒
```

三层防护，按重要性排序：

| 层 | 机制 |
|---|---|
| **1. 代码路径隔离** | 公开域函数只接受代码/日期/指标名，调用点写在读不到语料的代码里 |
| **2. 语料重叠检查** | 出境值与语料逐字比对（归一化后，改写标点绕不过） |
| **3. 格式检查** | 长度、字符集、换行、本地引用 —— **实测证明这层不足，只是防误伤** |

**一个诚实的记录**：格式检查曾让一段 45 字的完整语料段落顺利通过。
这个局限被固定成了一条测试（`TestFormatChecksAreNotEnough`），
免得后来的人以为格式检查够了。

**标的公司名本身也是机密。** 查 "宁波精塑 可比公司" 会在公开数据源留下
"你在看这家公司"这个事实。禁名表放在 `root/privacy-blocklist.txt`。
合规的替代方式是**用行业代码，不用公司名**。

## 早期项目：DCF 和乘数法都用不了的那一段

pre-revenue 的项目没有现金流，也没有 EBITDA。硬套的结果是分母为零或负数，
**算出来的数毫无意义，而且不会报错。**

所以早期项目要用另一套逻辑 —— 它估的不是现金流，是**风险和里程碑**。

```bash
python3 value.py examples/early-stage-demo.json
```

`value.py` 看到配置里有 `early_stage` 段就自动走这条流程，不用记两个命令。

| 方法 | 回答的问题 |
|---|---|
| **Berkus** | 去掉了几个风险？ |
| **Scorecard** | 比市场上的同类好还是差？ |
| **VC 法** | 要赚到目标回报，今天最多能付多少？ |
| **First Chicago** | 分情景看，概率加权是多少？ |

**三者的哲学完全不同，所以它们给出不同的数不是错误，是信息。**
演示里的差额是 189%，这本身就是该写进备忘录的结论。

### 两个锚点没有默认值

| 锚点 | 为什么 |
|---|---|
| Berkus 的「每因素封顶值」 | 原版是 **1990 年代美国西海岸的 50 万美元**。照抄到别的年份、别的地区是错的 |
| Scorecard 的「区域基准 pre-money」 | 是外部事实，算不出来。而且**市场冷热差一年，定价能差一半** |

给它们配"合理默认值"是最糟的设计：你会拿到一个看起来正常的数，
而它其实来自别人的市场、别人的年份。**所以不给就报错。**

### 稀释那一步最容易漏

```
今天占 20%  ≠  退出那天还占 20%
```

后续每轮都会稀释。忽略稀释会让 pre-money **偏高**，偏高幅度正好等于被稀释的部分。

而且方向反直觉：**稀释让投前估值变低，不是变高。**

> 投资者要 20% 的退出股权。若有 25% 未来稀释，今天必须占到 26.67%。
> 为同样的钱拿到更多股权 → 投后更低 → 投前更低。

这条写反了不会报错，只会安静地给出错的数。

### 有报价就跑反向

把「贵不贵」翻译成「要涨到多大」：

```
按这个价格，公司要在 5 年内做到 242,857 万元 的退出价值，即年化 70.2%。
**谈论这个数是否可信，比谈论估值高低有用得多。**
```

反向结果**不参与多方法差额** —— 它输出的不是估值，是「需要多大的退出」。
混进去算差额会得到一个毫无意义的数，而且看起来还挺像回事
（实测它把差额从合理的量级拉到了 199%）。

## 假设参谋：这个产品真正的位置

竞品都在做「帮你算得更快」。**没有一家在解决「这个 WACC 到底该填多少」。**

你给一个假设，系统告诉你：**这个数在同行里排第几分位、凭什么能成立、要什么证据。**

```
假设：预测期收入增长率 = 0.146   来源：管理层规划（CIM p.12）

对照：
  近三年收入 CAGR  （样本 4 家）
      P25 3.11%   中位 5.90%   P75 6.19%
      区间 -4.73% – 6.56%
    → 你的假设落在第 100% 分位
    → **高于 P75。** 需要明确说明凭什么能超过四分之三的同行
  来源：SEC EDGAR XBRL（上市公司官方披露）｜截止 2025-12-31 已披露

支撑这个假设需要什么证据：
  [A] 已签合同/在手订单（含金额与交付期）
          去哪找：销售合同、订单台账
  [A] 历史「量 × 价」拆解（至少三年）
          为什么：**增长来自放量还是提价，结论完全不同**
  ...
```

### 三条设计决定

**① 分布是真算出来的，不是编的。**

分位数来自 EDGAR 的实际财务数据。**编一个"行业平均 12%"和编一个
"公司未来增长 12%"一样危险。**

**② 拿不到分布就说拿不到，不凑参照系。**

没有可比公司时，输出的是「**不给你凑一个参照系**」——
硬凑的参照系比没有更糟，**它会让用户以为自己有了依据**。

**③ 证据清单是知识，不是猜测。**

写在 `EVIDENCE_LIBRARY` 里可以被审阅和修改，**不随模型随机性漂移**。

其中两条最该被追问的：

- **收入增长来自放量还是提价？** 价驱动依赖定价权，通常不可持续。
  只看增速数字看不出这个。
- **加回项是一次性的还是经常性的？** 把一次性开支的加回当成长期利润率，
  是最常见的估值错误之一。

### 永续增长的硬边界

**一家公司永远比整个经济长得快，在数学上不成立。**

```
假设：2.50%
上界：长期名义 GDP 增速 4.50%
✓ 通过

假设：4.30%  → ⚠ 已接近上限，需要说明凭什么有持续定价权
假设：6.00%  → ⚠ 超过长期名义 GDP 增速，数学上不成立
假设：1.00%  → ⚠ 低于长期通胀，等于假设公司长期实际在萎缩
```

最常见的错误是拍一个 3–4% 的永续增长，却没意识到
**「3% + 通胀」已经顶到长期名义 GDP 了**。

## 材料格式：PDF、HTML、Excel 都能读

```bash
python3 freeanalyst.py ingest <材料目录>   # .txt / .md / .pdf / .htm / .html 一起收
python3 freeanalyst.py ask --model qwen3:14b "有息负债和货币资金分别是多少？"
```

| 格式 | 状态 | 依赖 |
|---|---|---|
| `.txt` / `.md` | ✅ | 零依赖 |
| **`.htm` / `.html`** | ✅ **正文 + 表格 + 官方 XBRL 标签** | **零依赖**（标准库） |
| `.pdf` | ✅ 文字 + 表格 + 页码引用 | 可选：`pip install pdfplumber` |
| `.docx` / `.xlsx` | ⬜ 未做 | — |

**这是全项目唯一一个依赖，而且只在 PDF 用。** 不装它，其余部分照常工作。

### 为什么 HTML 值得单独做（而不只是"顺手支持一下"）

PDF 要跟字体子集、压缩流、没有结构的坐标搏斗。
HTML 是**有结构的** —— `<table>` 就是表格，难度差一个量级。

而真实材料的形态恰好是这样分的：

- **CIM / 尽调材料 → PDF**
- **上市公司申报文件 → 全是 HTML**（SEC 不发 PDF 版）

所以支持 HTML 等于把「上市公司财报」这条线整个打通。

### SEC 的 HTML 里白送了两样东西

**① 官方 XBRL 标签**

```html
<a onclick="top.Show.showAR( this, 'defref_us-gaap_AssetsCurrent', window )">Total current assets</a>
```

每个数字旁边就写着它的**标准科目名**（`us-gaap:AssetsCurrent`）。
于是「三张表科目映射」在 SEC 文件上变成**查表**而不是**猜**：

```
Cash and cash equivalents  →  us-gaap:CashAndCashEquivalentsAtCarryingValue
Total assets               →  us-gaap:Assets
Accounts payable           →  us-gaap:AccountsPayableCurrent
```

**② 可对账的机器可读版本**

同一份财报，`companyfacts` API 提供官方数字。
于是可以**拿自己的解析结果跟官方数据对账** —— 合成样例做不到这件事。

### 对账结果：三张表 89/89

拿 Fitbit FY2016 10-K（真实申报文件）跑：

```
合并资产负债表    25 项一致 / 0 项不符
合并利润表        19 项一致 / 0 项不符
合并现金流量表    45 项一致 / 0 项不符
```

### 顺带查出两个会翻转盈亏的 bug

**① `$ (102,777)` 的负号被吃掉**

原来先判断"是不是以 `(` 开头"，而 `$ (102,777)` **以 `$` 开头** ——
括号判断失败，括号被当普通字符剥掉，**负数变正数**。

```
19  Net income (loss) attributable...  '(102,777)'    → -102777
21  Net income (loss) attributable...  '$ (102,777)'  →  102777   ← 错
```

**亏损会显示成盈利，且不报错。** 一家亏 1.03 亿的公司显示成赚 1.03 亿。

**② SEC 会把一个数字拆进多个 `<td>`**

```html
<td colspan="2">(3,552</td><td>)</td>
```

不拼回去，`(3,552` 又会被解析成**正** 3552 —— 同一类错误。

两个都是靠跟官方 XBRL 对账才发现的。**看不见的错最危险。**

### 一个必须说清的坑：符号约定差异

现金流量表有 9 行对不上，但**不是解析错误**：

```
XBRL 标签  IncreaseDecreaseInAccountsReceivable = +8,701,000   「增加额」
现金流量表列示                                    (8,701)      「占用现金，取反」
```

独立验证：应收账款 469,260 → 477,825，**增加 8,565** ✓ 吻合。

**同一件事，两种符号约定。** 这直接说明：科目映射**不能只按标签取值然后比符号**。

### 还有一个必须说清的坑：标签不是一对一

`us-gaap:CommonStockValue` 在 Fitbit 的资产负债表里**出现两次** ——
A 类股（18）和 B 类股（5），而 XBRL 用一个标签给合计（23,000）。

**所以「标签 → 数值」不是一对一映射**，按标签取值反推某一行会错。

### `companyfacts` 给的是"最新视图"，不是"当时那版"

```
期末 2016-12-31  Total assets
  该年报原文（2017-03-01 申报）      1,820,226
  companyfacts                      1,821,926
                    申报日 2018-03-01  ← FY2017 年报重述过
```

差 1,700（千美元）。核对一份具体年报时必须限定披露日（`filed_by=`），
否则会看到一堆"不符"，**而且差异长得很像自己的解析错误**。

### 曾经的限制：跨语言检索不工作（**已解决**）

10-K 是英文的，最初用中文提问 BM25 检索不到（词面匹配，没有跨语言能力）：

```
中文提问 → 命中"员工人数""诉讼"等无关片段 → 模型诚实回答"材料未提供"
英文提问 → 命中正确的财务报表 → 数字全对
```

模型没有编（这点是对的），缺的是检索层的跨语言能力。
**v0.6 用「术语表扩展查询」补上了，两个方向都通了 —— 见下面的「中英文都能用」。**
留这一段是因为它记着一个判断：那个「材料未提供」的回答是对的，
**错的是检索，不是模型** —— 不修检索而去换模型，问题会一直躲在原地。

## PDF 部分的细节

### 为什么用 pdfplumber 而不是 pdftotext

对财务三张表，**表格结构比文字重要得多**。`pdftotext` 会把资产负债表抽成流式文本，
行列对应就丢了 —— "3,180" 到底是货币资金还是应收账款，从文本里看不出来。

`pdfplumber.extract_tables()` 保留行列网格：

```
【第 1 页 · 表 1】
| 项目 | 2025-12-31 | 2024-12-31 | 2023-12-31 |
| 货币资金 | 3,180 | 2,640 | 1,980 |
| 应收账款 | 6,420 | 5,880 | 4,510 |
```

### 有一个坑必须说：抽出来的中文，码位经常不是你以为的那个

```
抽出： 货币资⾦        ⾦ 是 U+2FA6（康熙部首金）
正确： 货币资金        金 是 U+91D1

抽出： ⻓期借款        ⻓ 是 U+2ED3（CJK RADICAL LONG）
正确： 长期借款        长 是 U+957F
```

**看着一样，`==` 比较是 `False`。** 后果是科目名对不上、检索命不中 ——
**而且不报错。** 整条流水线看起来在跑，结果是错的。

一份 1079 字的测试财报里有 **18 个字符**受影响。

修法是两层：`NFKC` 能处理康熙部首（那批有 compatibility 分解），
但 **CJK 部首补充区里有 113 个字符没有 NFKC 映射**，其中一批会作为正字
出现在中文正文里（长/民/日/月/目/西/虎/雨/青/足/骨/鬼/竹…），
所以另配了一张手工核对的映射表。

**没把握的一律报出来，不猜** —— 猜错比不处理更糟。

### 页码引用

PDF 抽取时会写入页码标记，所以引用能精确到页：

```
[S7]  test-financials.pdf 第 1 页
[S11] test-financials.pdf 第 1–2 页
[S2]  sample-cim.txt 第 5 段        ← 没有页码信息就报段落
```

**这里改过一次**：原来标签是 `source#p5`，模型看见后写成「页码 p5」——
**把段落号误读成了页码**。现在标签自己带页码，段落号也不再写成容易误读的 `#pN`。

### 扫描件：自动走 OCR

图片型 PDF 的文字层是空的。**这时自动用 macOS 内置的 Vision 框架识别**，
不再是「抽不到就直说」了。

| | |
|---|---|
| 费用 | 免费 |
| 网络 | **零出境**（纯本地，无模型下载） |
| 语言 | 原生支持 **zh-Hans / zh-Hant**、英文 |
| 速度 | 约 0.4 秒/页（34 页 13.7 秒） |
| 代价 | **只能在 macOS 上跑**。Linux 上会明确报「跑不了 OCR」并说明原因 |

#### 两件必须做对的事

**一、坐标配对。** Vision 把表格的左列（科目名）和右列（金额）返回成
两个独立文本块。直接顺序打印会变成「先全部科目名、再全部金额」——
完全没法用。实测某资产负债表 105 个文本块，顺序输出是 1–76 行标签、
77–133 行数字。所以按 boundingBox 的 y 坐标聚成行、行内按 x 排序。

**二、金额格式校验。** OCR 会认错标点。实测抓到的真例子：

    原文 334,719.50  →  OCR 认成 334.719.50

不校验的话，`_to_number` 会把它剥成 `33471950` —— **差 100 倍且不报错**。
财务数据上这种静默错误比明显报错危险得多。

#### 系统性错误可以修，随机错误不能

实测发现这份扫描件的错误**不是随机的**：千分位逗号被稳定认成句点或空格。

    334,719.50    →  334.719.50
    1,609,705.35  →  1.609.705.35
    85,748,813.69 →  85 748 813 69

错误模型确定、判据严格（每个分组恰好 3 位、末组恰好 2 位小数），
所以可以修，而且修完还能用勾稽校验反证。**判据不明确的一律不修**：

    45.508.51239  →  不修（末组 5 位，归不了位）

修复数会单独报出来 —— **静默修复和静默凑数一样不可接受**。

#### 分列：标签不是「第 0 列」

中文财报里**普通科目名左对齐、合计行右对齐**（贴着行次列）：

    货币资金        x=0.177
    流动资产合计     x=0.271      ← 同一个视觉列，但 x 差得很远
    资产总计        x=0.288

按 x 聚类会把它们分成两列，只取最左列就取空了 —— 于是所有合计行都变成
「〔此行没有标签〕」，资产总计、负债合计全丢，**勾稽直接判不了**。
正确做法：标签 = 第一个数字列**左边的一切**。

「行次」列（1、2、3……）也不能当金额，否则整张表错位。

#### 实测：34 页纯扫描件，两条勾稽全平

```
34 页 / 25,234 字 / 全文走 OCR
  24 处系统性错标点已按明确判据修复；71 处判据不明确，已剔除而非猜

资产 = 负债 + 所有者权益       ：平   150,066,441 = 150,066,441
期末现金 = 期初+经营+投资+筹资  ：平     6,840,705 = 6,840,705
净利润 → 经营现金流（间接法）   ：不适用（该表用直接法编）
```

**OCR 出来的页码会记进 `ocr_pages`，报告里明说「数字请人工复核」。**
和原生文字一视同仁是不诚实的。

入库时也一样：**没能读进来的材料全部列出来，不静默跳过**——
少了材料会让后面的问答以「材料里没写」来解释这个缺失，
而实际上是根本没读进来。

## 中英文都能用（跨语言检索）

中文提问配英文材料、英文提问配中文材料，**两个方向都要能工作**：

```
中文问英文 10-K   →  "2016财年的营业收入、营业利润…"
英文问中文 CIM    →  "What was the target company's revenue in 2025?"
```

### 做法：术语表扩展查询，不是翻译

跨语言检索有三条路：

| 做法 | 问题 |
|---|---|
| 让本地大模型翻译查询 | 每次结果可能不一样；多一次推理（qwen3:14b 要 70 秒）；**不可审阅** |
| 入口时把材料整份翻译 | 921 个片段逐个翻；译文质量被永久冻结；材料一变就得重来 |
| **术语表扩展查询** | 覆盖的是**封闭词汇集** |

选第三条，因为这个场景有个特殊条件：**财务术语是数得清的。**
「营业收入 / revenue」「应收账款 / accounts receivable」「毛利率 / gross margin」——
不像自由文本那样无边无际。

好处是确定、可审阅、零依赖、零延迟。`glossary.py` 就摆在仓库里，
200 条术语，**开源用户可以自己加自己行业的词**。

```
中文问：2016财年的营业收入、营业利润、净利润、总资产分别是多少？
扩展后：… + revenue operating income net income total assets
        → 命中英文 10-K，四个数全部正确
```

### 两条必须处理的细节

**① 长词优先。** 「营业**利润**」里含「**利润**」。两个都扩展的话，
查询里会多出一个**独立的** `income` —— 会命中大量无关片段。
按词长从长到短匹配，被长词覆盖的位置不再匹配短词。

**② XBRL 标签也要扩。** 「总资产」除了 `total assets` 还该带上 `Assets` ——
后者是官方标签，索引里的表格标题带它（见上面 HTML 那节）。

### 已知边界

术语表覆盖的是**词汇**，不是**语义**。
「哪块业务拖累了毛利」这种问题，术语表给不出跨语言桥接 ——
那种情况要靠材料本身有双语表述，或者你自己用材料的语言提问。

## Excel：小企业报表的真实格式

**中小企业的财务报表几乎都是 Excel**，而且是用 WPS 存的**老二进制 `.xls`**
（`openpyxl` 读不了，要 `xlrd`）。上市公司的年报才是 PDF。

```python
from financials.from_excel import load_excel_statements
S = load_excel_statements(["资产负债表2024.xls", "利润表2024.xls"], unit="元")
```

判断哪个文件是哪张表**不看文件名**，看内容（文件名太不可靠 ——
实测有个文件夹叫 `1财务报表`，sheet 名叫 `第12页`）。

### 坑一：资产负债表是「左右两栏」的

中文小企业的资产负债表是 T 型布局，**一行里同时装着资产和负债**：

```
[0]货币资金 [1]1 [2]21,470,366.19 [3]24,781,633.06 | [4]短期借款 [5]51
```

左边四列是资产，右边四列是负债及所有者权益。
**所有按「一行属于一张表」的解析器在这里都会错。**

更隐蔽的是：不切开会**混起来而且不报错** —— 标签取自左栏、行次取自右栏，
货币资金的行次会变成短期借款的 51。

判据：表头行的**值列名重复出现两次**（`行次/年初数/期末数` 各两组），
以第二个科目名列作为切分点。

### 坑二：列的顺序不是固定的 —— 而且歧义是静默的

| 表 | 列 1 | 列 2 |
|---|---|---|
| 资产负债表 | **年初数** | 期末数 |
| 损益表 | **本月数** | 本年累计 |

**资产负债表的「年初数」在前。** 照搬「取第一个数值列」会把
**去年的数当成今年的**，而且不报错 —— 这是本项目最不能容忍的一类错误。

所以列的角色**从表头读**，主数值列永远排到第 3 位，
同时把原文列名记进 `StatementSet.columns`，让报告能说清「这个数取自哪一列」：

```
资产负债表：本表列：期末数、年初数
    ↑ 主数值取「期末数」，不是「年初数」
```

### 坑三：小企业在用 1993 年的「行业会计制度」

实测一份真实标的（某小企业，2021–2024 四年报表）：

```
会工01表 / 会工02表              ← 工业企业的表号
一、产品销售收入 / 产品销售成本      ← 不是「营业收入 / 营业成本」
待摊费用 / 预提费用                ← 2006 年准则已废止
应付工资 / 未交税金                ← 旧名（现为应付职工薪酬 / 应交税费）
损益表（不是利润表）
```

**科目名和现行准则完全不是一套词。** 第一次跑，损益表 17 个科目只认出 6 个（35%）——
不是「看不懂」，是**用词不同**。补上旧制度的名字之后：

| | 修前 | 修后 |
|---|---|---|
| 资产负债表 | 32/57 | **39/57** |
| 损益表 | **6/17** | **16/17** |

### 实测结果：四年，全部 100% 映射，四条勾稽全平

```
年份    资产负债表        利润表         资产=负债+权益   净利润
2021   60行/60映射     16行/16映射     平            16,497,085
2022   60行/60映射     16行/16映射     平             5,695,070
2023   60行/60映射     16行/16映射     平            14,877,990
2024   60行/60映射     16行/16映射     平             9,102,006
```

**这份材料没有现金流量表**（小企业不编，旧制度也不要求）。
所以现金勾稽跑不了 —— 报告会说「未提供」，不会假装。

### 依赖

- `.xlsx` → `openpyxl`
- `.xls` → `xlrd`（老二进制 BIFF，`openpyxl` 读不了）
- 两者都是**可选**的：不装就只是读不了那种格式，其余功能照常。

## 三张表：科目映射 + 勾稽校验

**「理解三张表每一行」是这套系统里最贵的一块** —— 因为会计科目不是确定清单，
公司会自创科目名。所以这一层必须有个**客观的验收标准**，不能靠人看。

勾稽关系就是那个标准（`financials/`）：

```
资产 = 负债 + 所有者权益
期末现金 = 期初 + 经营 + 投资 + 筹资（+ 汇率影响）
净利润 → 经营现金流的间接法调节
```

**平了，说明映射对了。平不了，差额能帮你定位是哪一行错了。**

### 不是每条勾稽对所有格式都适用

三种情况实测都碰到了，**必须分开报**，因为对用户的意义完全不同：

| 情况 | 报法 |
|---|---|
| 材料缺了关键行 | **数据不足** —— 要去补数据 |
| 这种格式本来就没这条 | **不适用** —— 不用管 |
| 差额不为零 | **不平** —— 映射错了，别用结果 |

合并成一个「判不了」是最坏的做法：用户分不清该去补材料还是可以放心。

#### 一、现金流量表的调节段，A 股和 H 股都没有

**A 股**是**直接法**编的（「销售商品、提供劳务收到的现金」），
没有「净利润 → 经营现金流」那段调节 —— **那段在附注里**。

**H 股**主表也常没有：只列一行「经营活动所用现金净额」并挂个附注号，
真正的调节表在附注（实测某 H 股公司是附注 22(b)）。

两种情况硬跑都会报「定位不到锚点」，看着像映射漏了。
**现在都报「不适用」。** 但要注意区分：**有调节段、只是找不到终点**，
那才是真的「数据不足」—— 那时候是映射没抓到，要去查。

#### 二、H 股资产负债表用 IFRS「净资产列报式」

某 H 股公司 2020 年报的财务状况表**根本没有「资产总计」和「负债合计」行**：

```
非流动资产 … 小计
流动资产   … 小计
流动负债   … 小计
流动资产净额            = 流动资产 − 流动负债          1,887,814
总资产减流动负债         = 非流动资产 + 流动资产净额      2,317,397
非流动负债 … 小计
资产净额               = 总资产减流动负债 − 非流动负债    2,314,754
权益总额                                           2,314,754
```

所以 `资产 = 负债 + 权益` **用不了**，顶上来的是等价校验
**`资产净额 = 权益总额`**（2,314,754 = 2,314,754 ✓）。

**这里踩过一跤**：`Total equity attributable to equity shareholders of the Company`
（母公司权益 2,311,864）被错当成「权益总额」，差正好是一个少数股东权益
（2,890）—— **差额长得就像个小尾差**。根因是双语标签交错 + 中文折行，
拆出来的候选片段「权益总额」同时匹配了两行。

处置：给母公司权益加上更具体的片段名（`本公司权益股东应占` 等）。
候选顺序本来就是「从具体到宽泛」，所以会先命中具体的那条。

**还有一条**：`ok` 只由校验自己的主张决定，旁路复算只进 note。
用旁证决定 `ok` 的话，「母公司权益被错当成权益总额」会显示成「平」——
因为旁证那一侧仍然对，错的那一栏就被掩盖了。

#### 三、少数股东权益的口径

CAS 的「所有者权益合计」**已经包含**少数股东权益，美股 `StockholdersEquity`
是母公司口径。写死一种算法会差一整个少数股东权益 ——
实测某白酒公司差 **93.2 亿**（差额恰好等于少数股东权益，才反查出根因）。
现在两种口径都试，哪种平就用哪种。

#### 已知限制：合并表与母公司表印在同一页（扫描件）

**症状**：勾稽不平（或判不了），而且同一个科目出现两个取值。

**根因**：审计报告常把**合并报表和母公司报表印在同一页**（左右两栏，或上下相接）。
OCR 抽出来是两张表的科目混在一起，同一个科目拿到两个数，取值取串了。
实测某 A 股审计报告（249 页纯扫描件）**21 个科目**出现多个取值，
`期末现金 = 期初 + 经营 + 投资 + 筹资` 因此不平。

**它会报警，不会静默出错。** 这是刻意的：不平就拒绝给结论 —— 数看着正常、
只是全部错了，是这类材料最危险的失败方式，所以宁可停下。
`freeanalyst.py appraise` 还会把成因直接点出来（"这批材料有 N 个科目出现多个取值，
很可能是同一页上既有合并表又有母公司表"），让人知道从哪下手。

**现在怎么办**：把母公司那几页挑出来单独放，或者人工核对取的是合并那一列。

**要真正修掉需要**：从 OCR 版面切列、判断"这一页里有两张表"、
再按"合并表排在前面"取合并列 —— 属于提取层的下一次攻坚，**没做**。
记录在这里，是因为它现在是个**已知的边界**，而不是一个还没遇到的意外。

### 真实结果（Fitbit FY2016 10-K）

```
资产 = 负债 + 所有者权益    ：平    1,820,226 = 1,820,226
期末现金 = 期初+经营+投资+筹资：平      301,320 = 301,320（含汇率影响 -374）
净利润 → 经营现金流（间接法）：平      109,534 = 109,534（段内加总 20 行）
```

**这不是"跑通了"，是"验过了"。**

### 差额真的能定位问题

上面第二条一开始是**不平的，差 -374**。这个数太小，不像映射错误 ——
顺着它查，发现是漏了「汇率变动对现金的影响」那一行：

```
535,846（期初） − 234,152（净增加）+ (−374)（汇率）= 301,320  ✓
```

而且净增加额的 XBRL 标签叫 `...IncreaseDecrease**ExcludingExchangeRateEffect**` ——
官方标签本身就说明了汇率是单独一行。补上映射即平。

### 间接法为什么不逐行映射

那段有十几行（折旧、摊销、股份支付、各项营运资本变动…），逐行映射既费力又容易漏。

改成**把两个锚点之间的行全部加总**：

```
净利润 + Σ(中间各行) = 经营现金流
```

这样即使某一行没被识别，校验依然有效 —— 验的是**整段的完整性**，
不是逐行的正确性。小计行要排除，否则一段加两遍。

### 两条锚

| | 怎么映射 |
|---|---|
| **美股** | 官方 XBRL 标签是**确定答案**，SEC 申报文件的 HTML 里内嵌了标签 → 查表 |
| **中国材料** | 按企业会计准则科目名映射 + 别名覆盖 → 建表 |

### 推出引擎要的口径时，缺数据必须报缺

`financials/derive.py` 把三张表推成 DCF 要的几个口径（净债务、少数股东权益、EBITDA）。拼不全时：

| 做法 | 后果 |
|---|---|
| 缺的按 0 | 净债务偏低 → 股权价值偏**高** |
| 用行业平均填 | 得到一个看起来正常、实际无据的数 |
| **报缺**（选这个） | 用户知道要去补什么 |

**往好看的方向偏是最危险的 —— 它不会引起怀疑。**

而且每个口径都带构成明细（`短期借款 4,100 + 长期借款 2,300 − 货币资金 3,180`），
不是给一个没法核对的孤零零的数。

## 模型质量门槛

评测脚本在 `bench/model_quality.py`。五个用例覆盖五类会直接导致错误结论的问题：

| 用例 | 考的是什么 |
|---|---|
| **单位纪律** | 自行换算会引入 10 倍量级的错误，而且前面那个数还是对的 |
| 主体识别 | 实控人的**个人**回购义务，不能说成公司的负担 |
| 跨文档冲突 | CIM 写的条款和访谈中锁定的常常不是一回事 |
| 格式遵循 | 输出要进投委会，结构不稳定就没法进流程 |
| 拒答幻觉 | 材料里没有的文件，不许替它写结论 |

```bash
python3 bench/model_quality.py --models gemma3:12b-it-qat --json bench/results.json
python3 bench/model_quality.py --rescore bench/results.json   # 判分逻辑改了之后重判，不用重跑模型
```

### 实测结果（M4 Air / 24GB）

| 模型 | 体积 | 得分 | 单问耗时 |
|---|---|---|---|
| `qwen2.5-coder:7b` | 4.7 GB | 1/4 | 7 s |
| `qwen3:30b-a3b` | 18 GB | 2/4 | 80 s |
| `gemma3:12b-it-qat` | 8.9 GB | 3/4 | 13 s |
| **`qwen3:14b`** | **9.3 GB** | **4/4 ★** | **71 s** |

**`qwen3:14b` 过了门槛**，而且体积只有 9.3GB —— **18GB 的 qwen3:30b 反而不行。**

代价是慢：它也是思考模型，单问 71 秒（gemma3 只要 13 秒）。
但**做尽调不是做客服，71 秒换一个不会搞错主体的答案，值。**

连跑三轮复现性验证：**4/4、4/4、4/4** —— 不是一次好运。
原始答案在 `bench/results-qwen3-14b-run*.json`，可以自己核。

### qwen3:30b-a3b 为什么反而更差

它是 MoE（激活 3B），四个用例里**两个返回空字符串**：
2620 个 token 全烧在思考上，然后自认为说完了，答案一个字没出。
在 24GB 机器上还疯狂换页（系统空闲内存只剩 12%）。

**大不是好。** 而且"能跑起来"和"能给答案"是两件事。

### 选型建议

| 场景 | 用哪个 |
|---|---|
| 要过质量门槛的正式分析 | `qwen3:14b`（71 s，可接受） |
| 交互式快速检索、草稿 | `gemma3:12b-it-qat`（13 s，3/4） |
| 别用 | `qwen3:30b-a3b`（又慢又差）、7B（会编内容） |

### 关于评测器本身

**假阴性比没有评测更危险。** 修正判分逻辑的过程中发现的真实问题：

| 类型 | 实例 |
|---|---|
| 假阴性 | 「公司**不承担**，因此对公司**无**财务压力」——完全正确，却被判成"把个人义务说成公司负担" |
| 假阴性 | 「公司本身**不直接承担**回购的财务压力」——同样正确，同样被判错。**这个差一点让 qwen3:14b 被淘汰** |
| 假阳性 | 「确认函的内容，**仅表明**董事长表示回去找一下」——正确回答，却被判成编造 |
| 漏判 | 「公司将面临**回购**压力」逃过检查，因为旧模式要求中间出现"财务/现金流" |

**报错文字不准的代价是真实的**：它会让你以为问题比实际严重，或者反过来放过真错的。

**一个教训值得记下来**：这条规则我调了三轮还在漏 ——
加否定词、加语序约束，每次修好一个就漏出另一个。

> 兜圈子是因为在解一个**开放集合**问题：
> 「哪些说法算把义务说成公司的」是说不完的。
>
> 换成**要求式检查**（"结论节必须明确排除公司"，封闭集合、可判定）
> 之后就不漏了。正则退居次要，只用来抓最直白的形态和给出准确的失败原因。
>
> **当一条检查规则调了三轮还在漏，问题不是规则不够细，而是评判的角度选错了。**

**改判分逻辑时不该重跑模型**（慢，而且引入采样随机性）。
用 `--rescore` 拿同一批答案重判——答案没变，变的只是尺子。
但**尺子本身也要被测**（`tests/test_model_quality.py`，20 项）。

### 单轮结果不够 —— 要连跑几轮

`temperature 0.1` 下模型**仍有措辞抖动**：实测 5 个用例里
3 个三轮逐字一致、2 个措辞有变化。判定结果虽然三轮一致，
但单轮 5/5 不足以说明稳定。

```bash
python3 bench/model_quality.py --models qwen3:14b --repeat 3
```

```
  每轮得分：5 / 5 / 5   （满分 5）

  逐用例通过率：
    单位纪律         3/3
    主体识别         3/3
    ...
```

**各轮不一致时，结论要用最差那轮** —— 生产里没有"重跑一次"这个选项。
所以判定写的是「未达门槛（最差 N/5）」而不是平均分。

## 数据源：先接免费的官方源

**全部走公开域闸门，拿不到本地语料。**

| 市场 | 源 | 状态 |
|---|---|---|
| 美国上市公司（财务） | **SEC EDGAR** | ✅ 已接入 |
| 股价（A 股 / 港股 / 美股） | 东方财富历史日线 | ✅ 已接入（`prices.py`） |
| A 股 / 港股（财务） | AKShare / Tushare | ⬜ 待接入 |

**股价这一层已经通了** —— 它补的正是 EDGAR 没有的那一半：
市值 = 股本 × **基准日**收盘价，于是 EV、EV/EBITDA 这些倍数算得出来。
`prices.py` 有三条硬纪律：**按日期取价**（不提供"当前价"——你会在一个周二下午
把今天的股价配上去年 12 月 31 日的资产负债表）、**只取不复权价**（配同一时点的
股本才对）、**绝不返回基准日之后的日期**（防前视）。美股的市场前缀靠探测 + 缓存，
因为映射表不成立（沃尔玛是纽交所的，却挂在 105 下）。

### SEC EDGAR 为什么值

免费、无需 API key、无需注册，而且是**官方结构化数据**（XBRL）——
不用让大模型去"读"年报。

```bash
export SEC_USER_AGENT="你的机构名 你的邮箱@example.com"   # 必须带邮箱，否则 403
```

```python
from datasources import sec_edgar as se

cik = se.ticker_to_cik("AAPL")                    # 代码 → CIK
facts = se.company_facts(cik)                     # 全部 XBRL 数据
se.annual_series(facts, "Revenues")               # 年度序列
se.derive_ebitda(facts, "2025-12-27")             # 推算 EBITDA
se.frames("Assets", "CY2024Q4I")                  # 一次拿 6,000+ 家公司
```

`frames` 是可比公司筛选的现成答案 —— **一次调用返回同一科目、
同一期间、所有申报人的值。**

### 三个已实测确认的坑

| 坑 | 症状 | 处理 |
|---|---|---|
| **不带邮箱** | HTTP 403，且 SEC 不解释原因 | 本地先报错并给指引 |
| **请求了 gzip 不解压** | `UnicodeDecodeError: 0x8b`，看着像编码问题 | 按魔数解压 |
| **年度值和季度值混在一起** | 数据不报错，但季度值被当成年度值 | 按 start→end 时长分档 |

第三个坑最阴险。同一个标签、同一个期末挂着多条数据，区别在时长：

```
FY2025 营收   2024-09-29 → 2025-09-27   364 天   ← 年度
同期单季      2026-03-29 → 2026-06-27    90 天   ← 季度
同期累计      2025-09-28 → 2026-06-27   272 天   ← 9 个月 YTD
```

**实测 Apple 的营收标签有 117 条数据点，只有 21 条是年度值。**

### 标签会废弃，数据会静默停在旧年份

Apple 的 `Revenues` 标签数据**停在 2018 年** —— 它后来换用了
`RevenueFromContractWithCustomerExcludingAssessedTax`。
只试一个标签，拿到的是八年前的数，而且不报错。

所以推算科目（营收、EBITDA）都按优先级试多个候选标签，
**返回用了哪个标签**，让人能核对。

### EDGAR 没有股价 —— **由 `prices.py` 补上**

| EDGAR 能给 | EDGAR 给不了（由价格源补） |
|---|---|
| EBITDA、收入、净利、总资产 | 市值 ← 股本 × 基准日收盘价 |
| 跨公司同年份横向对比 | 企业价值 EV |
| 每股收益、股数 | **EV/EBITDA** |

**EDGAR 有财报，没有市值。** 要做市值倍数必须配价格源 ——
现在配的是 `datasources/prices.py`（东方财富历史日线，按基准日取不复权价），
`valuation/comps.py` 就是用它把「一家公司 → 市值 → EV → 倍数」串起来的。
留这张表是因为它记着当时的判断：**缺口要写在明面上**，
否则半年后没人分得清「算不出来」和「忘了配」。

## 快速开始

两条路：**要估值就走第一条**，要问答就走第二条。

```bash
# ── 路一：估值（材料目录 → 报告，全程不碰 JSON）──
# 1. 把材料放进一个目录（CIM / 年报 / 三张表 / 扫描件都行）
ls ~/deals/某个标的/

# 2. 第一遍：认材料 + 出问答清单
python3 freeanalyst.py appraise ~/deals/某个标的/
#    → 认出三张表、判出单位与口径、勾稽跑一遍、
#      再把「必须你给的假设」写成一份可填的 txt
#    → 产物统一落在 out/<标的>/（配置、问答清单、报告都在那儿）
#      **材料目录只读** —— 工具不往你的材料库里写任何东西

# 3. 填那份 txt（历史参考写在注释里，引擎不替你填假设）

# 4. 第二遍：出报告
python3 freeanalyst.py appraise ~/deals/某个标的/ --answers 估值问答.txt
#    → DCF + 敏感性 + 乘数法 + Football Field 的数据，带完整追溯

# ── 路二：问答（材料 → 本地索引 → 带出处的回答）──
ollama pull qwen2.5-coder:7b            # 没模型也能跑估值，只是不做问答
python3 freeanalyst.py ingest ~/deals/某个标的/
python3 freeanalyst.py ask "调整后 EBITDA 是怎么算的？回购条款对投资方有利吗？"
python3 freeanalyst.py audit            # 查这次到底有没有东西出网

# ── 路三：不想敲命令，就用浏览器（同一套计算，只是换了层皮）──
python3 freeanalyst.py ui ~/deals/某个标的/
#    → 开一个只在本机的页面：丢材料 → 提取核对 → 填假设 → 出报告
```

### 网页向导（`ui`）

**它只是一层皮。** 底下跑的跟命令行那条路**是同一套函数**
（`intake.scan` → `intake.build_config` → `value.run_report`），
有一条测试专门逐字比对"走网页出的报告"和"走命令行出的报告"，必须一模一样。
界面层不许自己再算一遍数 —— 那是两套数开始分岔的起点。

**只绑 `127.0.0.1`，不绑 `0.0.0.0`。** 绑了的话，同一个 WiFi 下任何人都能打开
这个页面、进而读到这台机器上的尽调材料。这条是红线（`webapp.py` 里有一条测试盯着）。

**六步向导，这一版做到第 1、2、5、6 步**（丢材料 / 提取核对 / 假设清单 / 结论）。
中间两步 —— 行业建议、可比公司选取 —— 需要先把流程层接进来，**还没做**，
页面上照实标注、不做成"看起来能用"。可比公司代码能在第 5 步的「可选」里填，
那一条是通的。

页面上能改口径三项（GAAP / 合并或单体 / 已审计或未审）—— **机器只推，改由人定**。

**没引任何 Web 框架**：`http.server` 够用（一次一个人用、只在本机、每步同步），
引一个框架进来只会让"能审计"这件事变模糊。

**`appraise` 这条路是 2026-09-23 接上的。** 在此之前，估值只能靠
`python3 value.py <配置 JSON>` —— 而那份 JSON 的形状是给程序看的，
得有人手写；更硬的是 **PDF 和 Excel 材料进不了那条路**
（配置里的 `statements` 节只认「一张表一个文件」的 HTML）。
现在 `intake.py` 把这条链接上了：认材料、列问题、拼配置，三件事。

**零第三方依赖。** 只需要 Python 3.10+ 和一个本地模型。

模型层用 OpenAI 兼容接口，不绑定后端——Ollama、LM Studio、vLLM、llama.cpp
都可以，换机器不用改代码。

## 估值引擎

```bash
python3 value.py examples/valuation-demo.json
```

**纯代码计算，不用模型算数。** 估值是确定性数学——让大模型去算会算错，而且
算错了你查不出来。模型在这个流程里只做两件事：把材料抽成数字、给假设找依据。

已实现：

| 模块 | 内容 |
|---|---|
| **WACC / CAPM** | Hamada 去杠杆/再加杠杆、规模溢价、国家风险溢价，逐项带来源 |
| **DCF（FCFF）** | 逐年驱动因子、永续增长法与退出倍数法双终值、二维敏感性矩阵 |
| **反向估值** | 从对方要价反推隐含永续增长率 —— 尽调里最有用的一件工具 |
| **乘数法** | EBITDA / SDE / 收入；可比公司分位数汇总 |
| **SDE 构建** | 从净利润倒推到 Seller's Discretionary Earnings，逐项调整可追溯 |

三条纪律贯穿全部代码：

1. **每个假设必须带来源和置信度。** 没有来源的假设是隐性炸弹——它不报错，
   但会让结果偏掉，事后无从判断错在哪。
2. **缺数据就说缺。** 桥梁项（少数股东权益、非经营性资产）缺失时按 0 计算，
   但会同时出现在「数据缺口」清单里。**禁止静默填充。**
3. **算不出来就报错。** 核心输入缺失、永续增长率 ≥ WACC、基数为负——
   这些都直接拒绝计算，不给出一个看起来正常的错数字。

测试用手算的已知答案验证（26 项），不是"跑通了"，是"算对了"：

```bash
python3 -m unittest tests.test_valuation -v
```

**需求基线见 [`docs/valuation-spec.md`](docs/valuation-spec.md)。**
它记的不是"我们要做什么功能"，而是"**什么情况下这个估值才是可信的**"——
功能可以增删，那些条件不能绕过。新增估值相关功能前，对照它的检查清单过一遍。

## 为什么机密不只是"公司名"

大多数人做保密设计，想的是"别让外人看到标的企业叫什么"，所以他们的办法是
把公司名替换成"标的企业A"再送到云端。

**这条路是错的。** 因为机密不在名字，在语义组合——收入、增速、EBITDA 率、
行业里只有三家可比标的、我们正在看其中一家。这组数字本身就是指纹。

而真正值钱的，是**你的判断框架**。所以 `root-templates/` 那套东西，
比任何单个 deal 都更需要保护。

## 质量门槛：本地模型够不够格？

"能不能跑"和"能不能用"是两件事。小模型能让流程跑通，但会犯三类致命错误：

| 错误 | 为什么致命 |
|---|---|
| **主体搞混** | 把实控人的个人回购义务说成公司的财务压力 → 结论反向 |
| **跨文档冲突检测不出来** | CIM 说条款已定，访谈纪要里对方其实有保留 → 尽调的全部价值就在这 |
| **编造内容** | 材料里没有的文件，它替你把结论写出来 → 比没有助手更危险 |

所以我们不靠感觉换模型，靠一组**固定会失败的用例**：

```bash
python3 bench/model_quality.py --models qwen2.5-coder:7b --show-answers
```

```
  [失败] 主体识别
        ↳ 把个人义务说成公司负担：「公司面临较大的财务压力」
  [失败] 跨文档冲突
        ↳ 未引用访谈纪要 —— 说明未做跨文档比对
  [通过] 格式遵循
  [失败] 拒答幻觉
        ↳ 结论节编造了材料中不存在的内容：「已闭环」

  小计：1/4 —— 未达门槛
```

**全绿才算够格进生产。**

判分刻意做得比关键词匹配严格：**按节解析**（某一节写得漂亮救不了另一节说错话）、
**来源覆盖**（跨文档那条必须同时引用两边，只引一边说明压根没比对）、
**语义模式**（覆盖整个表述族，而不是死盯一个固定说法）。

如果你要换模型，**先用一个已知不合格的模型跑一遍**——如果它全过，说明评测失效了，
这比模型不合格更严重。
