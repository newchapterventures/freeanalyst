FreeAnalyst · 标准 agent 架构对照
把六个标准部件逐项对到真实代码路径上。结论先说：它不是一个标准 agent，是一个「确定性内核 + 两个 LLM 算子」的专业管线，外面套了一层极厚的护栏。 自主性被刻意做低 —— 而尽调要的正是可复现、可追溯。
超配　护栏 · 评测 半个　LLM 核心 · 记忆 · 工具 缺　编排循环 · 技能体系 没有　MCP · ACP
六个标准部件，逐项对右边是判定和差距
01
LLM 核心大脑 · 推理
对应物：llm/backends.py（Ollama / 任意 OpenAI 兼容端点，只走回环）。 但它被刻意限制在两个位置：把材料抽成数字、给假设找依据。估值算术一律不走模型——"让大模型算会算错，而且算错了你查不出来"。
有 · 被降级为算子
02
编排循环harness / agent loop
没有循环。freeanalyst.py ask 是单轮：检索 → 生成 → 挂出处。估值链是确定性流水线：Scenario → 提取 → 假设 → DCF → Football Field，谁调谁由代码写死。 这是与"标准 agent"最大的差别 —— 它不会自己想"下一步该干什么"。
缺
03
工具tools / tool schema
能力都在，但形态是 Python 模块：datasources/sec_edgar · prices · retrieval · financials · valuation。 全仓库 没有任何 tool_calls / tool_use / function_call —— 也就是说：手脚长在身上，但模型没有"自己伸手"的通道，伸手的是代码。
有手脚 · 无模型调用
04
记忆memory
工作记忆：index/chunks.json 本地索引 + 材料语料（BM25 + 术语表扩查询）。 没有跨会话长期记忆 —— 每次都是一份新材料重新开始。对尽调这个场景，这未必是缺点（不串案子）。
半个
05
技能skills / 操作手册
没有 SKILL.md 体系。等价物是三样硬编码的东西：代码里的流程、EVIDENCE_LIBRARY（证据清单知识表）、root-templates/ 的 12 份空白判断框架。 这恰恰是"技能"的雏形 —— 只是写死在代码里，用户改不了、也不随行业更新漂移。
形态不同
06
护栏guardrails
六件里唯一超配的一件：guard.py 唯一出网口 · net.py 公开域白名单 · privacy.py 跨域唯一入口（出境值与语料逐字比对 + 禁名表）· 按次授权 · 全量审计。 而且多了一类标准架构里没有的护栏：纪律护栏——缺数据报缺、不用 LLM 算数、门槛裁决用最差轮。
超配
附：第七件——评测。标准架构里经常没有这一层，它反而是全项目的重心：bench/model_quality.py 五类致命用例 + 33 个测试文件 638 项 + 判分的尺子自己也被测（20 项）。 连"格式检查不够用"这种自我否定，都被固定成了一条测试。
界面：几个，都是什么实际可用的 vs 只有设计稿的
入口能做什么状态
1freeanalyst.py主 CLI：ingest 入库 · ask 提问 · models 看模型 · audit 审计 · doctor 自检可用
2value.py估值引擎 CLI —— 但输入是一份手写的 JSON 配置（假设、三张表路径、可比公司 ticker 都在里面）可用 · 有门槛
3valuation/football_demo.pyFootball Field 渲染 —— 区间是演算数据，用来验证图和数据结构对不对演示件

8docs/interface-mockup.html六步向导：1 丢材料 · 2 提取核对 · 3 行业建议 · 4 可比公司 · 5 假设清单 · 6 结论，每一步都是"程序准备好、你点头才往下走"只有设计稿
9网页 / 桌面 app / API都没有。部署四阶段只走到第 1 阶段（源码运行）无
协议：MCP 和 ACP 都没有但要不要加，两个答案不一样
MCP · 没有
Model Context Protocol —— 昨天讲过的"插座"
全仓库唯一的痕迹是两句自述：CHANGELOG「未提供 MCP server，接入 Claude Code / Cursor 等宿主需自行封装」，README Roadmap 里一个没勾的框。既没有 server 也没有 client。

加了会怎样：FreeAnalyst 从"一个你要学命令行的工具"变成一套能被别的 agent 直接调用的能力——你在 Hermes 或 Claude Code 里说一句"把这份 CIM 跑一遍估值"，背后调的是它的 ingest / 提取 / run_dcf。
判断：值得做，而且优先级排在向导之后 —— 因为它同样能替你消化掉"手写 JSON"那个断点。
ACP · 没有
Agent Client Protocol —— 编辑器 ↔ agent 的协议（Zed 发起，JetBrains 共同维护）
本地 agent 以子进程 + JSON-RPC over stdio 接入编辑器；已成熟到 v2 draft、Rust/TS SDK 1.0、注册表（2026-04 发布）。它的定位是"把你的 agent 装进 IDE"。

对 FreeAnalyst 用处有限——你不需要在 Zed 里做尽调，你需要一个能走完六步的网页。
但有一个细节值得记：ACP 在 2026-07 把 Elicitation（agent 向用户要结构化输入）稳定了 —— 那正是你"假设层"缺的那件事。只是为它接 ACP 属于绕远路，自己做个表单更直接。
判断：现在不做。
别把两个 ACP 搞混：现在说 ACP 一般指 Agent Client Protocol（Zed / JetBrains，编辑器侧）；还有 IBM 早先的 Agent Communication Protocol（agent 之间通信，已并入 AGNTCY）。FreeAnalyst 两个都没有。
若要"标准 agent 化"，缺的是这三件而且顺序不能反
01
补编排循环：把六个步骤变成 agent 的"待办"
每一步准备好 → 问用户 → 点头才往下（mockup 里已经这么写了）。循环只负责编排与提问，算术仍然交给确定性内核——这样既拿到 agent 的灵活性，又不把可复现性赔进去。
02
工具化：把那 12 个模块包成带 JSON Schema 的工具
这一步同时解决"手写 JSON 配置"的断点，也是 MCP server 的前置条件。做完这个，MCP server 几乎是顺手的事。
03
技能化：把判断知识从代码里搬出来成文档
现在"人力外包毛利率是个位数、EV/Revenue 会严重失真"这类知识写在 comps_workflow.py 里。变成可审阅、可编辑的文档，才能加行业、才能让别人贡献，而不是每次改代码。
但先说清楚一件事：不做这三件，FreeAnalyst 也能是完整的产品。 尽调要的是可复现、可追溯、不幻觉 —— 标准 agent 的"自主性"在这个场景里是负债不是资产。 所以这三件不是"补课"，是在自主性和可复现之间划一条线：编排可以有循环，算术不能有随机。
